# Происхождение производных признаков company_profile

Все признаки строятся детерминированными правилами, без LLM. Код: `services/company_profile/features.py`, параметры: `services/company_profile/config/feature_rules.yaml`.
Каждый признак в профиле содержит `rule_id`, `based_on` (файл, строка, поле, значение), `confidence` и `rationale`. По этим полям можно восстановить, почему признак принял своё значение (критерий 12 кейса).
Шкала `level`: `high | medium | low | none | unknown | info`. Значение `unknown` означает, что данных для вывода не хватает, а не что влияния нет.

Общее ограничение: признак отвечает на вопрос «через какой канал событие может касаться компании». Он не утверждает, что событие принесёт компании ущерб или выгоду. Пороги — эвристики прототипа, а не методология банка.

## rate_sensitivity — чувствительность к ключевой ставке (`rate_sensitivity_v1`)

Поля: `CL_PRODUCT_LOA_MARK`, `CL_PRODUCT_LEA_MARK`, `CL_PRODUCT_GAR_MARK`, `FACTORING_MARK`.
Правило: если есть кредиты или лизинг, уровень `high`; если есть только гарантии или факторинг, `medium`; если все флаги равны 0, `none`; если часть флагов пуста, `unknown`.
Confidence: `medium` для `CL_TYPE = CLIENT`, иначе `low`, потому что смысл флагов у потенциальных и бывших клиентов не подтверждён.
Не знаем: тип ставки (фиксированная или плавающая), объём долга, сроки. Поэтому формулировка в rationale звучит как «влияет на стоимость обслуживания и рефинансирования», без оценки величины.
Темы: `key_rate`, `credit_conditions`, `bond_market`.

## deposit_income — доход по депозитам (`deposit_income_v1`)

Поле: `CL_PRODUCT_DEP_MARK`. Если флаг равен 1, уровень `medium`; если 0, `none`; если пуст или некорректен, `unknown`.
Темы: `deposit_rates`, `key_rate`, `liquidity`.

## fx_and_trade_exposure — курсы, санкции, логистика (`fx_trade_v1`)

Поля: `FTS_FLAG`, `FTS_COUNTRY_NAME`, `OKFS_NAME`.
Правило:
- `FTS_FLAG = 1` или заполнен список стран → `high`;
- данных ФТС нет, но собственность иностранная → `low` (слабый косвенный сигнал);
- флаг равен 0 → `none`;
- иначе → `unknown`.

Направление ВЭД (импорт или экспорт) всегда `null`, потому что в данных его нет. Если флаг и список стран противоречат друг другу (430 компаний), confidence снижается до `low`, а в rationale добавляется предупреждение.
Темы: `fx_rates`, `sanctions`, `logistics`, `foreign_trade`.

## payroll_exposure — рынок труда и зарплаты (`payroll_v1`)

Поля: `AMOUNT_WORKERS_FNS_GRADATION`, `CL_PRODUCT_ZPP_MARK`.
Правило: градация численности по ФНС задаёт базовый уровень: «Менее 15» → `low`, «16-100» → `medium`, «101-250» и «Более 251» → `high`. Если зарплатного проекта нет, уровень понижается на одну ступень, потому что меньше уверенности, что ФОТ заметен в обороте.
Численность по СПАРК не используется: она заполнена у 0,2% компаний.
Темы: `labor_market`, `wage_inflation`.

## consumer_exposure — потребительский спрос (`consumer_v1`)

Поле: `MAINOKVED_CODE`. Совпадение одного из уровней кода с префиксами `47`, `55`, `56`, `45.11.2`, `45.32`, `79`, `93`, `96` даёт `high`, иначе `none`.
Группа `45.3` целиком не берётся: в неё входит и опт автозапчастей. Ошибка была замечена на реальной компании из демо-набора и исправлена.
Связь с материалом банка «Потребление на пике» устанавливается через темы `consumer_demand`, `inflation`, `retail`. Само сопоставление темы с материалом делают участники 2 и 4.

## counterparty_concentration — концентрация контрагентов (`concentration_v1`)

Источник: `df_Uid_payment_hack.csv`. Самоплатежи исключены, повторные строки пар просуммированы.
Правило считается отдельно для входящих и исходящих платежей:
- видимых контрагентов меньше 5 → `unknown`;
- доля крупнейшего не ниже 0,5 → `high`;
- доля не ниже 0,3 → `medium`;
- иначе → `low`.

Итоговый уровень — максимальный из двух направлений. Confidence всегда `low`.
Почему стоит порог по числу контрагентов: на реальных данных медиана видимых партнёров равна 4, а медианная доля крупнейшего плательщика — 0,82. Без порога почти каждая компания выглядела бы «зависимой». Слова «критическая зависимость» правило не использует: банк видит лишь часть оборота, и период неизвестен.

## supply_chain_industries — отрасли цепочки поставок (`supply_chain_v1`, уровень `info`)

Источник: платежи плюс `MAINOKVED_CODE` контрагентов. Учитываются только контрагенты, которые есть в файле юрлиц.
Получатели исходящих платежей трактуются как вероятные поставщики, плательщики входящих — как вероятные покупатели. Это допущение: назначение платежа в данных отсутствует.

Состав `details`:
- **Сводка** `suppliers` и `customers` — до 5 классов ОКВЭД (2 цифры) по сумме, формат с версии 0.2.0.
- **Детализация** `supplier_codes` и `customer_codes` (с 0.3.0) — агрегаты по полному коду ОКВЭД. В каждом есть `okved_levels`, поэтому префикс новости сравнивается точным равенством уровню кода. Id контрагентов в детализацию не входят.
- **Лимит** `top_codes = 50` кодов на направление по сумме. На реальных данных p90 различных кодов — 43, максимум — 332. Если коды обрезаны, это видно в `*_codes_meta.truncated` и `omitted_share_of_known`.
- **Покрытие** `known_coverage_outgoing` и `known_coverage_incoming`. Если покрытие ниже 0,3, confidence становится `low`.

Правила точного совпадения (`industry_terms.match_supply_chain`, `match_company`):
- `"45.3"` совпадает с 45.31.1 и 45.32;
- `"45.32"` не совпадает с 45.31.1 (сосед);
- `"41.20"` не совпадает с менее точным кодом 41.2, а `"41.2"` совпадает с обоими;
- некорректные префиксы (`"4"`, `"45."`, `"45.3.1"`) вызывают `InvalidOkvedPrefix`.

Темы:
- `rule_shares` — для каждого отраслевого правила доля известного оборота, где ОКВЭД контрагента совпал с префиксами правила по уровням кода. Считается по **всем** кодам, а не по обрезанному списку; берётся максимум по двум направлениям.
- Правило с долей не ниже 0,2 даёт свои темы с весом `0.5 × доля`.
- До 0.3.0 сопоставление шло только по двузначному классу, и правила с глубокими префиксами (`07.29.4`, `46.46`) на контрагентах не срабатывали. Это исправлено.

## Темы профиля (`topics`) и веса

Темы собираются из трёх источников:
- отраслевые правила `industry_topics`, вес 1,0;
- признаки уровня `high` (вес 0,8) и `medium` (вес 0,5);
- цепочка поставок (вес 0,5 × доля отрасли).

Для каждой темы сумма весов ограничена 1,0, а все источники перечислены в поле `sources`. Ранжирование (участник 4) может объяснить, почему тема важна, ссылкой на источник.

## Отраслевые темы и разделы ОКВЭД

Разделы ОКВЭД2 (буква по диапазону классов) взяты из ОК 029-2014. Правила вида «префикс ОКВЭД → темы» лежат в `industry_topics`. Код сопоставляется по уровням иерархии, поэтому `41.2` и `41.20` обрабатываются корректно.

Правило `precious_metals` исправлено: префикс `46.72.2` удалён (в данных это «металлы в первичных формах»), добавлен `07.29.4` (добыча руд драгметаллов, сверено с данными).

## Как добавить отрасль или правило без изменения кода

1. Добавить запись в `industry_topics`: `id`, `okved_prefixes`, `topics`. Префикс может быть любого уровня, например `07.29.4`.
2. Если нужна новая тема, внести её в словарь тем в `docs/company_profile_contract.md` и сообщить участнику 4.
3. Пороги меняются в `thresholds`, префиксы потребительского сектора — в `factors.consumer_exposure.okved_prefixes`.
4. Запустить тесты: `uv run pytest tests/company_profile`. Тест `test_every_section_division_unique` ловит пересечение диапазонов разделов.

Новый тип признака (новый `code`) требует кода в `features.py` и PR в контракт (`FactorCode`).

## Что сознательно не используется

`NEGATIVEMARK` в профиль не входит вообще (с версии схемы 0.2.0): смысл поля не подтверждён организаторами, а неиспользуемые данные наружу не выдаются. Сырое значение хранится только в `company_profile.companies`, доступ к ней есть у ролей ETL и API. Геоданные физлиц не используются (минимизация данных; `RC_NAME` — это макрорегион). Состав мега-групп (больше 50 компаний) не используется для отраслевых выводов.
