# Метрики, мониторинг качества и масштабирование

## Метрики (`GET /api/metrics`)

| Группа | Метрика | Зачем | Порог/реакция |
|---|---|---|---|
| Контент | доля `needs_review`, число заблокированных (инъекции), неподтверждённых, устаревших | качество входного потока | рост доли `needs_review` > 10% — проверить парсер источника |
| Персонализация | доля 👍 среди оценок; число жалоб «не по теме» | релевантность | `useful_share` < 0,6 — пересмотреть веса в `ranking.py` |
| Персонализация | покрытие: доля компаний с ≥ 3 событиями выше порога (*предлагается, в `/api/metrics` пока не считается*) | не пропускать важное | < 90% — расширить правила тем/отраслей |
| AI-компонент | доля инсайтов с непройденной самопроверкой; доля отклонённых переписываний LLM; откаты на правила | надёжность | рост — разбор промптов/модели |
| AI-компонент | p50/p95 время сборки, токены за день | стоимость и скорость | токены > 80% бюджета — алерт |
| Использование | заявки/звонки по инсайтам, число вопросов | ценность | — |

## Регулярный процесс

1. **Еженедельно** эксперт размечает 30 случайных пар «компания × событие»: релевантно/нет, корректны ли тема и отрасль, верна ли позиция банка (по странице). Целевые пороги: релевантность ≥ 0,8; корректность атрибуции банка ≥ 0,95; фактологических ошибок — 0.
2. Каждая найденная ошибка становится регрессионным тестом (`tests/insight`, `tests/news_ingest`) и правилом в YAML.
3. Обратная связь пользователей (👍/👎 + причина) пишется в `feedback.jsonl` и сводится в `/api/metrics`.
4. При появлении нового документа банка якоря проверяются автоматически (`/api/health` → `anchors_rejected`).

## Масштабирование

* **Новая отрасль** — строки в `contracts/industry_terms.yaml` (термины → префиксы ОКВЭД) и, при необходимости, сценарий в `PLAYBOOKS` (`lenses.py`): данные, не код ядра.
* **Новая тема** — шаблоны в `news_ingest/config/topic_rules*.yaml`, тема в словаре; приоритеты ролей — `roles.yaml`.
* **Новый источник** — запись в `sources.yaml` (RSS/HTML) или адаптер «байты → Extracted»; резервные источники — несколько записей одного типа.
* **Новая позиция банка** — запись в `bank_anchors.yaml` (проверяется по тексту страницы при старте).
* **Типы клиентов** — профили строятся на лету для любой компании из CSV; `Prospect`/`Close Client` не обслуживаются (вопрос 12 вебинара).
* **Нагрузка.** Профили и индексы в памяти (≈0,5 ГБ на 85 тыс. компаний), лента — O(N материалов × признаков) на запрос с кешем инсайтов по версии базы знаний; для тысяч материалов — перенос поиска кандидатов в SQL (`NewsStore.search_candidates`), LSH для дедупликации, вынос сервера на ASGI/несколько процессов, PostgreSQL вместо SQLite (код хранилищ участников готов, не проверялся).
* **Сопровождение.** Правила — YAML под тестами; версии зависимостей — `requirements.lock.txt`; изменения — `CHANGELOG.md`.
