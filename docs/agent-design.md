# Дизайн агента

## Почему один агент, а не несколько

Задача линейная и ограниченная: «по клиенту и событию собрать доказательства и написать инсайт».
Мультиагентная схема (независимые агенты-исследователи, переговорщики) добавила бы
стоимость, недетерминизм и сложную отладку без выигрыша в качестве. Вместо этого — **один агент
с ролями на разных шагах** (plan / synth / critic), каждая роль — отдельный промпт и модель
из `config/models.yaml`. Роли можно заменить на отдельные модели или повысить их число, не меняя контракт.

## Цикл

```
[профиль + событие] → plan → tools* → synth → critic ──(fail)──▶ revision → critic
                                                  └──(ok)──▶ insight + trace
```

| Шаг | Что делает | Промпт | Выход |
|---|---|---|---|
| `plan` | выбирает инструменты и аргументы из белого списка `config/tools.yaml` | `prompts/plan.md` | список шагов |
| `tool` | вызов сервиса (profile / ranking / ingestion) | — | данные в трассу |
| `synth` | формулирует `claims` с `claim_type` и `provenance`, чипы вопросов | `prompts/synth.md` | `BusinessInsight` |
| `critic` | проверяет: каждый факт подтверждён фрагментом, нет нецифрованных утверждений | `prompts/critic.md` | pass / fail + замечания |
| `revision` | пересборка проблемных claims | `prompts/synth.md` | обновлённые claims |
| `followup` | ответ на вопрос пользователя только по собранным доказательствам | `prompts/followup.md` | ответ + claims |

Ограничения: `max_steps`, `min_evidence_per_claim`, `min_confidence` — в `config/thresholds.yaml`.

## Инструменты

Только из `config/tools.yaml`. Планировщик не может вызвать произвольный URL или LLM-функцию —
всё, чего нет в списке, отклоняется до исполнения.

## Самопроверка (критик)

1. Каждый `fact` и `inference` имеет ≥ 1 `provenance` с непустым `fragment`.
2. Фрагмент действительно присутствует в источнике (подстрочная/семантическая проверка).
3. Числа и даты в тексте claim встречаются в источниках.
4. `claim_type` не занижен (вывод не выдан за факт).
5. При `fail` — одна ограниченная ревизия; если и она не проходит, инсайт помечается пониженной
   уверенностью, а в трассе `critic_passed=false`.

## Трасса

`RunTrace` пишется на каждый прогон: шаги, вход/выход инструментов, версии моделей и промптов,
длительность, результат критика. Используется для отладки, аудита и объяснения в UI.

## Тестирование

- Заглушка LLM (`LLM_PROVIDER=stub`) возвращает детерминированные ответы на фикстурах
  из `contracts/examples/`.
- Сценарии: успешный прогон, провал критика и успешная ревизия, недоступный инструмент,
  prompt injection во входном новостном тексте.
